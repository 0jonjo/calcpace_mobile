# Plan

The goal isn't a super app. It's a small app that someone opens and thinks "nice app". It is also a portfolio piece. Every milestone ends with something shipped: a store release, a production deploy, and a short write-up.

## Phase 1: parity with the TWA (Android 2.0.0)

Replace the Trusted Web Activity without anyone losing anything.

- [x] Hotwire Native shell (1.3.1), single navigator, the site draws its own header and tab bar
- [x] Same `applicationId` (`app.calcpace.twa`), same icon, `versionCode` 3
- [x] calcpace.app App Links open in the app (assetlinks already serve the package)
- [x] External links open in a Custom Tab; `mailto:`/`tel:` go to the system
- [x] Edge-to-edge: the page stays clear of the status bar, gesture bar and keyboard
- [x] Google/Strava sign-in through a Custom Tab with a PKCE-bound one-time ticket, handed back by a verified App Link (`/app_auth/callback`); outside links can't load `/app_auth/*` into the WebView, however the path is spelled

## Phase 2: the native touches (Android 2.x)

Ordered by impact for effort.

1. **"Your run is in" notification** (in progress, `feat/push-run-arrived` here and in calcpace_web): a one-line summary when a Strava (later Health Connect) run arrives.
   - [x] Firebase options from a `google-services.json` outside the repo; CI builds with push off, release fails without it
   - [x] `push` bridge component, FCM token only after the athlete taps "turn on" (auto-init off)
   - [x] Data-only message → notification on a `runs` channel (16 languages); the tap only opens a same-site path
   - [ ] End to end on the emulator against the Rails branch (permission prompt, token registered, notification, tap cold and warm)
   - [ ] Real phone; then restrict the Android API key to the package and the Play signing SHA-1s

   Contract with the site:

   | Event (web → app) | Reply `data` |
   |---|---|
   | `connect` `{}` | `{ "status": S, "token": T? }` |
   | `enable` `{}` | `{ "status": S, "token": T? }`, after the system prompt |

   - `S` is `granted`, `default`, `denied` or `unavailable`:
     - `unavailable`: no usable Firebase in this build (no `google-services.json`, or a package other than `app.calcpace.twa`, such as `.debug`).
     - `granted`: the athlete tapped "turn on" in the app and the system lets it notify.
     - `default`: never asked, denied once, the prompt dismissed, or a permission granted outside the app without the tap; the system would still ask.
     - `denied`: blocked for good (second "Don't allow", or an instant refusal with no prompt drawn), or allowed but switched off in settings (app or `runs` channel).
   - `T` only comes with `granted`. The page posts `T` to `POST /push_devices` and shows its card only for `default`.
   - The app answers only when the WebView shows the home page (`/` or `/<locale>`); messages from any other page or frame are ignored.
   - A phone that opted in and then loses permission (`denied`, or `default` after a revoke) deletes its FCM token once. The server's next send comes back UNREGISTERED and it prunes the device; the next `granted` brings a new token. The server sends `{ "data": { "title", "body", "path" }, "android": { "priority": "high", "ttl": "86400s" } }`, where `path` is a site path such as `/pt-BR/activities/123`.
2. **Share card** (in progress, `feat/share-image`): an image of the run (map and key numbers) for Instagram stories, generated by Rails and shared through a bridge component and the Android share sheet.
   - [x] `share-image` bridge component: payload checks and allowed pages as pure rules on the JVM; the card written to `cacheDir/shared_images/` and shared through a FileProvider (`${applicationId}.shareimages`) and the system chooser
   - [ ] End to end on the emulator against the Rails branch, with the largest card ("with photo")

   Contract with the site:

   | Event (web → app) | Reply `data` |
   |---|---|
   | `share` `{ "filename": F, "data": D }` | `{ "ok": true }` once the chooser was started, or `{ "ok": false, "error": "invalid" \| "failed" }` |

   - `D` is the PNG in standard base64 (no `data:` prefix), at most 8 MB decoded (the page refuses bigger cards too: Hotwire parses every message on the main thread), starting with the PNG signature. `F` is 1–80 characters of `[A-Za-z0-9._-]`, ends in `.png` and doesn't start with `.`. Anything else: `invalid`. Writing the file or starting the chooser going wrong: `failed`.
   - The app answers only while the WebView's main frame shows a run's page (`/activities/<id>` or `/<locale>/activities/<id>`); messages sent while it shows any other page get no answer. Only the main frame's URL is checked, so an iframe on a run page could still send one; that's acceptable because a run page is only shown to its owner and embeds no third-party frames. A `share` that arrives while another is being prepared (a double tap) gets no answer either.
   - The PNG is decoded and written off the main thread to a fresh `cacheDir/shared_images/<random>/F` (older ones deleted first), so every share has its own content URI. If the page goes away meanwhile, no chooser and no answer; if the app went to the background, `failed` (the athlete taps again).
3. **Health Connect import** (in progress, `feat/health-connect` here, `feat/health-connect-import` in calcpace_web): runs and walks from Garmin, Samsung, Pixel Watch and others for athletes without Strava, which caps the API at 10 athletes.
   - [x] `connect-client` 1.1.0, WorkManager 2.12.0; five read permissions, no `WRITE_*` in release; privacy rationale activity (and the Android 14 alias) opening `/<locale>/privacy#health-connect`; tokens out of backups
   - [x] Pure rules on the JVM: wire format and batches, active duration without pauses, link-token format, allowed pages, privacy URL per locale, SDK status, what each HTTP answer means, sessions waiting for distance
   - [x] Reader (sessions + distance/HR/climb aggregated over each session, filtered to the recording app), worker (30-day initial read, then the Changes API), `health` bridge component
   - [x] Debug-only seed from adb (`HcSeedActivity`)
   - [ ] End to end on the emulator (API 35) against the Rails branch
   - [ ] Play Console: Health apps declaration and Data safety (Jonjo); real phone with Garmin/Samsung

   Contract with the site (fixed; calcpace_web follows the same):

   | Event (web → app) | `data` sent | Reply `data` |
   |---|---|---|
   | `connect` | `{}` | `{ "status": S, "linked": L, "background": B }` |
   | `enable` | `{}` | `{ "status": S, "granted": G, "background": B, "grant": N }`, after Health Connect's screen (or Play's, for `install_required`); `grant` only with `granted: true` |
   | `link` | `{ "token": T, "grant": N }` | `{ "linked": true }`, or `{ "linked": false }` if T is malformed or N isn't the open grant |
   | `unlink` | `{}` | `{ "linked": false }` |

   - `S` is `available`, `install_required` (install or update Health Connect from Play) or `unavailable`.
   - `L`: the app holds a link token. `B`: background reads exist on the phone and are allowed. `G`: `READ_EXERCISE` and `READ_DISTANCE` allowed (heart rate and climb are optional).
   - `T`: 43 base64url characters; the app refuses anything else.
   - `N`: a one-time grant, 43 base64url characters (256 random bits), handed out only in the reply to a granted `enable` (the reply reaches only the caller's callback in the page, not other frames). `link` is taken only with the latest `N`, once, within 5 minutes; any `link` closes the gate, right or wrong, so a guessed or missing `N` means a new `enable`. (Contract change agreed in review round 2; calcpace_web mirrors it.)
   - Only the home (`/`, `/<locale>`) and the account page (`/account`, `/<locale>/account`) may drive it.
   - Any frame of a page can reach the bridge, hence `N`. When exercise and distance were allowed before, Health Connect may show nothing, so the app asks for a native confirmation before answering `granted: true`; "Cancel" answers `granted: false`.
   - The page, on `enable` with `granted: true`, posts to `/health_connect/link` (cookie + CSRF), gets `{ "token": T }`, sends `link` with `T` and the `grant` of that `enable` reply, and reloads on `{ "linked": true }`. If `L` is true and the server has no link for this session, it sends `unlink`.

   Upload (app → server): `POST /health_connect/sessions`, `Authorization: Bearer T`, JSON, at most 50 sessions and 200 deleted ids per request:

   ```json
   { "initial": false,
     "sessions": [{ "id": "<metadata.id>", "type": "running | running_treadmill | walking",
                    "start": "2026-10-04T09:00:00Z", "end": "2026-10-04T09:53:10Z", "zone_offset": -10800,
                    "title": "Morning Run", "origin": "com.garmin.android.apps.connectmobile",
                    "device": "Garmin Forerunner 265", "distance_m": 10214.5, "duration_s": 3150,
                    "hr_avg": 152, "hr_max": 171, "elevation_gain_m": 48.2 }],
     "deleted": ["<metadata.id>"] }
   ```

   - `duration_s` is active time (pauses and rests taken off); `title`, `device`, `zone_offset`, `hr_*` and `elevation_gain_m` are left out when unknown.
   - The first sync sends the last 30 days with `initial: true` (never notified). The changes token is taken before that read and only moves on once every request of a sync got a 2xx (or 400/409/413/422: the server's final word on our payload). A changes token Health Connect expires or refuses means the 30-day read again. 429, 5xx and network errors retry with backoff; 401 makes the app forget its token and stop.
   - A session with no distance yet is re-read by id on later syncs and given up after 48 h; a read that fails for any reason other than "not found" keeps it pending. Deleted ids all go (Health Connect doesn't say what they were).
   - `DELETE /health_connect/token` (Bearer) → 204: the app gives the link up when exercise or distance permission is revoked in Health Connect.
   - Known limit: apps that don't write pause segments (likely Garmin) get elapsed time, not moving time.
4. **Home screen widget:** the week's distance and runs, and the next race.
5. Native bottom tabs and toolbar, with the web versions hidden in the app.
